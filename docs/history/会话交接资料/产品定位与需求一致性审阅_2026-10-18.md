## 2. 产品究竟如何定位

### 2.1 建议采用的定位表述

**一款本地优先、由用户掌控原文件的个人智能相册：通过可纠正的时间、地点、人物、内容和事件信息，帮助用户浏览、整理和找回照片与视频，并按需把素材整理成生活记录。**

这是对已有方向的收敛建议，不是新增产品决定。其依据是 S1 的“相册基础功能 → 体验分析 → 日志”结构，以及 S2 问题 39、S3 §1.1 的最终边界。

定位的重点应落在用户获得的结果：照片找得到、信息理得清、原件改动可控。模型管理、动态词条和双视图是实现这些结果的能力。

### 2.2 产品各部分承担什么角色

| 部分 | 对用户的价值 | 在产品中的角色 |
|---|---|---|
| 浏览照片、查看文件夹 | 立即查看已有媒体，知道文件在哪里 | 相册的基础体验 |
| 人物、地点、内容、事件分类与搜索 | 减少记忆文件名和手工分类的负担 | 智能相册的主要价值 |
| 一次性整理文件夹 | 把已经理解、分类的媒体整理到实际目录 | 用户主动调用的管理能力 |
| 事件与旅行理解 | 把零散媒体按一次经历组织起来 | 同时服务分类、检索和回顾的语义组织能力 |
| 日志、游记、Blog | 将选定媒体和已有信息表达为可编辑、可导出的记录 | 基于相册素材的内容产出 |
| 模型、任务、缓存和服务商设置 | 让能力适配设备、资源和个人选择 | 支撑能力 |

**这里的角色关系不代表开发先后顺序。** 地图与时间轴仍保留用户已明确的“高级、可后期制作”属性，其余功能不在本次分期。

### 2.3 需要避免的定位偏移

- 不应让用户为了日常看图，先学习词条、实体、逻辑媒体和推理后端。它们可以是内部概念，前台可以直接呈现人物、地点、事件和照片信息。
- 原始需求还包括有趣图片、笑点解释等用途。不能把所有媒体都默认解释为用户亲历的生活；截图、转存图片、他人发来的照片也需要自然地被管理。
- 事件不能被放到“将来写 Blog 才使用”的位置。S3 §7 的用户批注明确要求事件作为重要分类信息，这与智能相册主体一致。
- 可以保留完整模型配置能力，但它不应成为基础浏览和分类的前置步骤。定位仍然服务照片管理。

## 3. 需求之间有哪些冲突或没有闭合的规则

为避免把不同问题混在一起，以下区分：**文档状态冲突**、**操作语义缺口**、**能力覆盖缺口**和**需要验证的取舍**。发现缺口不等于已经选定修正方案。

### R01：重复文件归并已经被重新提出疑问，部分文档仍将它当作定案

**依据：** S3 §2.3、§8.1 的用户批注；对照 S2 §2、S4、S5 问题 17。

旧归纳把“多个相同文件映射到同一逻辑媒体”作为基础规则，带批注需求稿却明确写了“这个处理问题我还在思考”“重复的物理来源是一个大问题”。这是本次最明确的文档状态冲突。

应分别保留三件事：

- 视觉相似但不同的照片必须独立：用户已经明确强调。
- 已有多个实际文件时，移动、删除要指向具体文件：现有材料已明确。
- 完全相同文件是否共享逻辑身份、标签、事件关系及确认状态：用户重新保留了判断，不应继续当作既定前提。

**影响：** 虚拟视图数量、批量选择数量、照片信息编辑、删除、恢复和授权范围都会受影响。它是产品语义问题，不能只交给哈希算法决定。

### R02：“相同内容才共用逻辑媒体”与“修改 EXIF 后仍保留身份”缺少衔接规则

**依据：** S3 §2.3、§8.2。

例子：A、B 两份完全相同的文件原本共用一条记录；用户只给 A 写入新的拍摄时间。此时两份文件的字节内容已不同，但正文又要求元数据变更不产生新的逻辑身份。

这并非不可解决的根本矛盾，但当前“相同”究竟指文件字节、画面内容，还是同一张照片的不同版本，没有明确边界。若继续采用多来源模型，还必须说明不同来源出现不同元数据时，界面显示什么，以及编辑会影响谁。

**保留判断：** 合并、分离、共享信息及版本关系的具体规则，见 Q01。稳定身份的目标不能直接替代这些规则。

### R03：“从任意动态集合移除”不一定存在唯一、合理的操作

**依据：** S3 §2.2、§6.2、§8.3。

在单一“猫”分类中，移除可以明确为去掉“猫”标签。在“猫或狗”的结果中，一张照片同时拥有两者，去掉“猫”后它仍会出现。在“去年在上海”的结果中，让照片消失可能需要篡改真实时间或地点。

因此，“从条件集合移除 = 修改对应词条或关系”不能作为适用于所有查询结果的通用规则。任意动态查询通常不能唯一反推出应该修改哪条信息。

**建议方向，待判断：** 在能明确对应单个关系的场景中显示“移除猫标签”“解除与某事件的关联”；复杂结果中只提供含义明确的实际动作。若希望只让某张照片退出某个动态集合、又不改其信息，就需要额外的例外机制，这会改变当前纯动态集合的定义。

### R04：同类 OR 的规则明确，但不能覆盖所有直观的“同时包含”查找

**依据：** S3 §6.1—§6.4。

现有规则下，选择人物“小王”和“小李”，得到小王或小李出现的照片；用户也可能希望找的是两人同框。地点、内容等多值类别也存在类似差异。

这不是 OR 规则本身自相矛盾，而是“简洁筛选界面”与“联合查询覆盖范围”之间的缺口。若自然语言支持“两人同时出现”，需要解释它怎样与三态条件共同生效，不能把两种不同语义显示成同一组勾选。

**保留判断：** 保持同类 OR 为默认的前提下，是否以及怎样表达全部包含，见 Q03。本次不将它改成 AND，也不引入默认高级表达式编辑器。

### R05：“元数据 / checked / AI 默认”混合了来源与确认状态

**依据：** S3 §1.2 的用户批注、§4.3、§4.5、§6.3。

“从哪里来”和“有没有被人确认”是两件事。一条 AI 推断被用户确认后，既来自 AI，也已经确认；一条 EXIF 时间被用户确认后也同时具有两种属性。把三者视为互斥状态会丢失信息。

**建议方向，待判断：** 信息来源与人工确认分别保留；界面可以使用简洁标记。若用户本意只是显示一个主要徽标，也应保留查看原始来源的途径。

另一个待定点是：“仅已确认”是否包含未经人工检查的原始元数据。不能一方面称其为“仅人工确认”，另一方面又无说明地纳入所有元数据。

### R06：动态分类可自动变化，上传授权的变化边界没有写清楚

**依据：** S3 §2.2、§3.1、§4.2。

例子：用户允许“旅行”分类调用云端。以后 AI 自动把一张新照片归为旅行，是否也获得上传许可？用户当时授权的是当时那些照片，还是未来持续满足规则的照片？两种理解都会影响预期。

现有“已授权范围内可自动执行、禁止优先”可以与动态集合并存，但尚不足以回答上述问题。更进一步，重新分类、人工纠错、多个物理来源及已排队任务，都会改变有效范围。

日志生成和搜索还可能传输照片以外的信息，例如地点、人物名、视频转写及关联事件。仅限制“媒体文件上传”并不能完整描述这些任务实际传输的上下文。

**保留判断：** 动态授权是当前成员快照还是持续规则，以及派生信息与任务执行时的授权边界，见 Q06。这里是已要求的授权功能本身的语义澄清。

### R07：自动补充信息与人工纠错之间缺少防止反复覆盖的规则

**依据：** S3 §3.1、§4.5、§6.3、§7.3。

用户去掉错误的“北京”推断后，新模型再次分析是否会重新添加？用户取消一次人物关联，表示“这次识别错了”，还是仅撤销自己之前的操作？正文只写人工确认优先，尚未覆盖明确否定与撤销。

同时，搜索默认纳入 AI 推断，文章使用已确认事实，这两条可以相容；但不能让“搜到了素材”暗示这些素材上的所有信息都能作为已核实经历写进文章。

**建议方向，待判断：** 区分推测、确认、否定和撤销；生成文章时显式处理关键事实不足的情况。缺失的信息不应为了文章完整而被补成真实经历。

### R08：移动到扫描范围之外，可能导致刚整理的照片从 App 消失

**依据：** S3 §2.4、§3.2。

用户只扫描文件夹 A，却在整理时把照片移到 B。若 B 不在扫描范围，整理后它是否还受管理？若自动扩大扫描范围，又会改变用户原先限定的范围。

**保留判断：** 目标目录的权限与纳入索引应如何处理，见 Q08。扫描范围、系统访问权限和实际文件位置应分别解释。

### R09：隐藏相册的早期需求没有被完整追踪

**依据：** S1“相册分类”；S2 问题 23；S3 §3.2、§4.2。

最初想法提到隐藏相册有特殊要求，后来明确撤回的是本地应用锁、私密保险箱和身份验证。普通浏览中的隐藏、排除扫描，以及加锁保护含义不同。

现有材料不足以判断最初的“隐藏”是否全部被撤回，还是仍保留部分显示/扫描需求。不能擅自恢复保险箱，也不应默认为所有隐藏需求都已解释完毕。

**保留判断：** 仅记录这一需求追踪缺口，见 Q10。

### R10：多分类与单一物理目录目标需要明确转换

**依据：** S3 §2.2、§2.4。

同一张照片可以属于“旅行”“家人”“美食”，但一次移动只能给所选具体文件确定一个目标位置。仅移动、不内部复制的规则本身没有问题，问题是不能把所有虚拟归属直接逐一兑现为目录成员关系。

正文已经要求预览跨分类冲突，方向正确；仍需保留具体的目标选择规则。在此之前，智能混合规划是建议方案，不能被理解为自动解决所有多归属问题。

### R11：低资源与丰富智能能力属于取舍，现阶段不能承诺同时达到未定义的强度

**依据：** S3 §1.2 用户批注、§3.1、§4.1、§4.6、§9.3。

立即开始轻量分析、历史增量处理和模型按需加载并不矛盾；如果把它们解释成首次使用就完整运行所有识别、视频转写、向量索引和多模型任务，则会与用户特别强调的资源约束产生压力。

现有“前台浏览优先、可暂停、自适应调度”已提供协调原则。仍需验证默认模型能做什么、何时运行以及分析未完成时如何呈现。当前没有依据断言技术上不可行，也没有依据承诺所有设备都能快速完成。

### R12：“词条”覆盖了不同信息形态，统一入口不等于全部采用同一种筛选方式

**依据：** S1 的附加信息需求；S3 §4.3、§4.4、§6.2，以及 §7 的用户批注。

“人物：小王”关联具体对象，“标签：猫”描述内容，“事件：某次旅行”关联一次经历，“说明：一段文字”则是叙述。它们可以共用添加和展示入口，但长文本不一定适合作为枚举选项逐一勾选，事件也不宜因为叫作词条就丢失其层级和关系。

这不是要求再拆出几套界面，而是需要澄清“词条类别、具体值、对象关系和长文本”的含义。否则统一词条库容易同时承担字段管理、标签整理和人物事件管理，用户很难预测重命名或删除的影响。

**建议方向，待判断：** 统一用户操作入口，同时按实际信息类型提供合适的编辑、筛选或全文检索方式。事件作为分类维度，与事件仍具有独立的业务含义可以共存。

## 4. 哪些看似冲突，其实已经相容

| 表面差异 | 为什么可以共存 |
|---|---|
| 内部整理不复制，分享导出可生成副本 | 操作目的和作用范围已被明确定义，S3 §2.1、§8.4 已作区分 |
| 一次性文件夹整理，新增照片继续自动索引 | 一次性约束物理移动任务，自动索引负责持续发现媒体，S3 §2.4 已区分 |
| 不做本地锁，仍限制上传 | 本地访问控制与云端传输授权分别解决不同操作边界 |
| 时间地点可写回，不内置修图 | 元数据写入与像素、音视频内容编辑不同 |
| AI 可以给出相似组，相似照片仍保持独立 | 分组和对比不要求合并媒体身份；用户批注已强调独立性 |
| 搜索包含 AI 推断，文章避免虚构事实 | 探索性查找与以事实为基础的叙述可以使用不同标准，需要明确衔接 |
| 事件用于分类，Blog 是延伸 | 事件本身可组织照片；文章是使用这些关系的一种产出 |
| 自动开始本地分析，允许关闭自动分析 | 前者可以是默认流程，后者是用户对后续行为的控制；入口应可发现 |

## 5. 是否直观：按用户实际任务检查

以下属于基于场景的设计判断，不是已经完成的用户测试结论；交互建议均未定案。

| 用户任务 | 现有设计中合理的部分 | 可能不直观之处 | 建议方向 |
|---|---|---|---|
| 打开后先看看照片 | 渐进索引、无需等 AI 完成 | 首页只明确了目录/分类外层，未说明是否能直接看全部近期照片 | 保证有容易发现的全部照片浏览路径；不因此擅自新增主导航 |
| 按人物、地点找照片 | 动态聚合、不用手工搬文件 | “真实/虚拟”容易让用户误以为存在两套照片 | 可考虑“文件夹/智能分类”等表达，并解释分类不改变文件位置；命名留待用户判断 |
| 查看并修正照片信息 | 全屏后上滑，内容就近编辑，只显示有值字段 | “词条、实体、事件”全部外露会增加学习负担 | 面向用户显示人物、地点、事件、标签等具体概念，保留统一的添加入口 |
| 添加一个自定义信息 | 信息面板有统一添加入口 | 要用户先选数据类型、先建词条库会打断任务 | 从用户想补充的信息出发，复杂类型管理按需出现 |
| 组合筛选 | 三态、结果数量、一键清空 | 空白与未识别不相同；循环点击三种状态可能意外进入排除；同类 OR 不一定符合直觉 | 条件摘要用完整话表达，例如“包含小王或小李；排除截图”，保留当前状态和清除途径 |
| 看没有结果的查询 | 能实时展示命中数量 | 尚未分析和确实没有匹配目前可能呈现相同结果 | 让用户知道分析覆盖情况；不把“没有识别到”表达为“实际不存在” |
| 删除或移除照片 | 文档区分了三类操作 | 普通用户未必理解“删除逻辑媒体记录”；同一个删除图标不能承载三种含义 | 动作直接说明后果，例如“移除标签”“删除设备文件”；逻辑记录管理的入口与措辞待定 |
| 处理重复文件 | 可显式选具体物理来源 | 一张缩略图可能代表多份文件；照片数、文件数与释放空间不一致 | 在会改变设备文件的场景显示具体份数和位置；平时避免强迫用户理解底层身份 |
| 批量整理目录 | 预览、用户确认、进度和失败重试 | 分类结果与最终目录之间差异不易察觉 | 移动前同时展示来源、目标和实际文件数；未消解的冲突不包装为完整计划 |
| 缩放时间网格 | 双指之外有显式入口，保持时间位置 | D/M/Y 缩写对中文界面不够直接 | 可用“日/月/年”，并验证与图片本身缩放的手势边界 |
| 查看媒体信息 | 上滑展开、保持原图比例 | 固定约 1/3 和 2/3 不一定适配横屏、视频和键盘 | 保留“媒体预览 + 可编辑信息”的目标，具体尺寸需通过原型验证，不在本次改动已选方案 |
| 生成游记 | 任意选素材、使用模板或自定义提示词 | 选到素材不代表用户亲历，也不代表地点和人物均已确认 | 明确素材与事实依据，允许基于有限信息生成草稿，避免替用户编造感受与经历 |
| 导出有修正信息的媒体 | 原媒体与附加 JSON 可分别导出 | 用户可能以为 App 内修正的时间会自动进入分享出去的原文件 | 导出前说明是否包含 App 中的修正；具体输出策略留待判断 |

**直觉层面的主要风险，是用户在看图、分类、筛选和文件操作之间切换时，不清楚这一步会改变什么。** 保留双视图是可以的，但界面需要持续让操作后果清楚，而不是仅靠首次教程解释数据模型。

## 7. 对现有需求文档的后续修订建议

本次仅新增审阅文档，没有改写原始想法、交接材料、需求稿或决策 JSON。后续若用户接受本次分析，可据此修订：

1. 用用户任务解释产品定位，同时保留 Android 原生、本地优先、文件改动受用户控制的原则。
2. 将“重复文件归并为同一逻辑媒体”恢复为待判断，并同步检查摘要、索引与验收中依赖这一假设的条目。相似照片独立与明确文件操作对象继续保留。
3. 收窄 §8.3 对“从条件集合移除”的笼统承诺，为不同场景描述具体动作及影响。
4. 明确同类 OR 的能力边界，保留“同时包含”的需求判断，不擅自更改已选筛选规则。
5. 澄清来源与确认、动态授权与新增媒体、人工纠错与重分析之间的关系。
6. 明确事件直接参与分类和搜索；文章生成继续作为相册素材的延伸。
7. 把本清单中的产品规则与后续技术细节分别保留，避免用“交给实现处理”掩盖会影响用户操作的选择。

本次可以形成的审阅意见是：**保留整体方向，澄清具体动作会改变什么，恢复被过早定案的事项，并用实际任务验证交互。具体解决方案仍由用户后续判断。**
