## 1. 外部评审意见摘要

### R01 隐藏相册被删去

评审认为，最初想法将隐藏与图片、视频并列，并强调特殊要求；PRD 以不做本地锁、保险箱或身份验证为由撤掉隐藏，违背防止借手机时被看到私密照片的直觉。建议恢复隐私文件夹及密码或生物识别，不与复杂账号系统绑定。

### R02 网盘入口被收缩为本地备份

评审认为，原设想中“保存到某网盘”的入口没有保留，只剩 App 数据的本地备份；作为初期范围控制可以理解，但相对最初想法发生了收缩。

### R03 已较好保留的设想

- 只展示有内容的词条，并提供添加入口；原始元数据与用户输入采用统一的信息表达。
- 常居地、旅行路线、图文日志与时空体验得到保留。
- 以项目学习技术属于开发协作目标，未误写成面向用户的教学产品。

### R04 哈希识别与单副本 EXIF 写回冲突

评审指出：如果 A、B 按字节哈希归并到 L，而只向 A 写入 EXIF，A 的哈希就会变化；如果 L 又由哈希定义，会与稳定逻辑身份冲突。不能只把问题登记为待办而不明确模型边界。

### R05 多维分类映射到单个物理目录会冲突

评审指出：一张照片可同时属于家人和旅行，而单份文件只有一个实际位置；内部又不允许复制，若多维视图都要求映射落地，用户可能反复解决目标单选题，与减少操作负担的目标冲突。建议日常虚拟聚合为主，物理搬动作为主动工具。

### R06 “仅已确认”没有闭合原始元数据语义

评审指出：相机 EXIF 若不算人工确认，筛选可能排除大量正常照片；若自动算人工确认，又无法区分人工核验。需要分开信息来源和核验状态。

### R07 L、A/B、T 不宜成为用户认知前提

评审认为，开发内部可以存在逻辑对象、副本和任务，但普通浏览不应要求用户先理解这些抽象才能修改属性。建议像普通相册一样展示，必要时才展开文件副本。

### R08 去重动作表达过于复杂

评审认为，用户只想选出保留文件并删除多余副本，若界面充满“移出任务”“仅操作某份”“逻辑记录”等边界，会难以判断到底删没删。建议简化主交互，同时保留清晰结果。

## 2. 评估与已确认处理

| 意见 | 评估 | 用户确认后的处理 | v1.2 落点 |
|---|---|---|---|

| R02 | 是产品范围变化；原件托管与 App 数据备份是不同责任 | 用户明确产品不直接保管原件，删除网盘及相关远程备份同步需求；保留 App 数据本地备份 | §1.1、§9.1 |
| R03 | 保留；不因本轮结构变化删去这些能力 | 继承原需求；高级能力的开发阶段另行讨论 | §4.3、§7、§1.3 |
| R04 | 是需要闭合的规则，但哈希不必成为 L 的身份；全副本写回仍可能部分失败 | 属性先改 App；主动 EXIF 同步覆盖 L 全部已关联副本，更新各份哈希并保留 L，逐份报告结果。去重仍检查当前实际字节，不仅看共享 L | §2.3、§8.1—§8.2 |
| R05 | 多维视图与单位置并存本身不矛盾；若承诺无损物化所有分类，才无法满足。目标冲突与交互负担确实存在 | 日常统一虚拟主页，物理整理为可选 T；临时计划归属每文件唯一，重新放置替换旧目标，不暗中复制。冲突批量规则继续待判断 | §2.2、§2.4—§2.9、V11-Q02 |
| R06 | 问题成立；不能把来源等同于人工核验 | 常用开关改为“排除未确认的 AI 推断”，保留原始元数据及人工信息；按信息贡献筛选，不因另含未确认字段就整张排除 | §1.2、§6.3 |
| R07 | 内部模型有必要，用户界面不应展示开发符号作为学习门槛 | 普通主页按照片和属性展示；具体文件范围在详情、重复工具和执行预览中表达；T 仍按虚拟属性组织 | §2、§5、附录 A |
| R08 | 数据边界应保留，主交互应简化，二者可以同时满足 | 重复组支持批量选择保留/删除；允许待删除项进入 T，统一预览同步。未参与任务与删除仍需区分，但不逐 L 强制填写副本方案 | §2.9、§8.1、V11-Q02 |

“EXIF 全副本同步”是独立主动操作，可以覆盖 T 范围外已关联副本；T 的移动和删除仍只作用于明确纳入的实际文件。两者不能借用同一个范围默默扩大操作。

## 3. 讨论进一步形成的 T 工作区方案

### 3.1 主页面与分类安排

1. 放弃顶层真实/虚拟双视图，主页面始终是虚拟属性视图。
2. 用户主动进入 T，选择来源范围，初始化实际目录映射及全部范围内文件的归属；映射不复制照片。
3. T 里的媒体仍按人物、事件、词条、时间等组织，目标目录有“真实”标记。
4. 放入 axx 目录即为对应实际文件设置 axx 临时计划归属；再放入 bxx 则替换旧安排。
5. 初始化归属不等于本轮检查完成；区分本轮未处理与已安排，明确保留原位也可完成本轮安排。
6. L 永久属性、实际文件原始位置、T 临时目标分开。多份副本可以各有目标，不污染共享属性。

### 3.2 保存、继续、加载、重置、同步

| 动作 | 已确认含义 |
|---|---|
| 自动保存 | 保存最新工作区草稿；离开时自动保存，正常编辑也保持最新可恢复安排；不覆盖手动槽 |
| 手动保存 | 用户选择手动槽保存当前计划；覆盖已有槽须明确选择 |
| 继续 | 恢复最新自动草稿，继续未完成整理，不重新初始化覆盖计划 |
| 加载保存计划 | 可选择自动或任一手动槽，恢复当前工作区，不立即改变实际文件 |
| 重置到物理目录 | 按当前实际目录重新初始化当前工作区，放弃待同步安排；不移动文件，不回滚已执行操作，不覆盖手动槽 |
| 同步到设备 | 显示移动和待删除差异，经确认才执行并记录逐文件结果；不是后台双向同步 |

保存固定为 **1 个自动保存槽位＋3 个手动保存槽位**。这是当前工作区的保存总额度，不按每个 T 无限增殖，也不提供额外无限历史。槽位保存引用、目录映射、临时归属、处理状态和计划，不存一套原照片、缩略图或模型。

用户提出槽位限制时担心快照开销。限制按产品决定保留；尚未测量开销，不能据此断言快照很大或需要四份原图库。

重置后按自动保存规则更新自动槽，旧自动草稿不再保证保留；手动保存计划仍可选择加载。若同步已经部分成功，重置依据当前已变化的磁盘，不是最初目录。

加载旧计划不能恢复已删除的文件，不能跳过当前文件状态和权限检查，也不能把历史执行结果当作本次授权。自动槽作为加载目标时，应先读取选中的内容，避免被当前工作区的自动保存覆盖后再读。

### 3.3 重复删除进入计划

用户已选择允许重复副本进入 T 的待删除计划。标记、保存、离开、加载都不实际删除；同步预览列出保留与删除名单。退出任务范围不是删除。删除前复核当前重复关系与可保留副本，文件的移动和删除最终意图不能冲突。

## 4. 已闭合与仍待判断的界限

产品定位、统一主页、T 的临时归属、保存/同步区分、自动与手动槽、加载范围、重置含义、待删除计划、EXIF 同步范围、常用筛选及隐藏边界已有方向性结论。不再将它们反复列为开放选项。

以下仍待后续判断，保留在 v1.2 的问题追踪中：

- 重复文件自动归并、原有信息冲突、外部编辑后的身份与重新关联。
- 批量保留哪份副本、同名目标和目标冲突的默认处理；用户尚未选定目录优先级。
- 保存计划遇到外部移动、权限失效、动态查询变化时，怎样刷新或合并。
- T 内永久属性编辑的提交与撤销语义；加载计划不承诺回滚 L 的永久属性。
- 复杂属性层级、严格人工核验、否定/撤销/重分析等细节。
- 隐藏密码与会话实施、本地备份隐私边界；普通媒体云端授权实施细节。
- 本地模型具体选型、人物匹配质量、体积、设备性能和 Android 文件权限可行性。
- 实际交互是否足够直观，需要原型与真实照片试用验证，不能以文档闭合代替测试。
